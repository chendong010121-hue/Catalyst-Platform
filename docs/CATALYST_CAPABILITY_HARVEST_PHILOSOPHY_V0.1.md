## Purpose

This document explains a possible way to preserve valuable capability as Catalyst evolves. It is a design interpretation only. It does not add a Platform object, layer, service, ontology, pipeline, or implementation requirement, and it does not claim that the capability-harvest model is already implemented.

## 1. Preserve capability, not implementation

Catalyst is not primarily designed to preserve software. Catalyst is designed to preserve capability. Models, providers, Agents, Harnesses, Runtimes, adapters, tools, frameworks, and other implementations may be replaced. What should remain portable where sufficiently understood and evidenced is the capability itself: domain knowledge, enterprise meaning, evidence and evaluation knowledge, workflow patterns, compatibility and migration knowledge, and operational learning.

This is an interpretation of Catalyst's asset-preservation and replaceability principles. It is not a replacement architecture and does not make every implementation an organizational asset.

## 2. Understand before preserving

Useful capability must become understandable enough to evaluate and preserve. A review should ask what a system does, what responsibilities it carries, what is valuable, what is accidental, what evidence supports the claim, what can survive replacement, and how it could be reused. Catalyst does not claim universal understanding. A design direction must remain distinct from a proven implementation.

External Agents, tools, projects, workflows, and other systems may be sources of useful capability. Their conceptual inclusion does not imply universal support, automatic onboarding, or a new Platform boundary.

## 3. Evaluation is evidence, not a leaderboard

Evaluation is not primarily a leaderboard. It determines what is proven, what remains uncertain, what limitations apply, what maturity has been reached, and what caused a failure. `UNDERSTAND` is not the same as `HARVEST`; evidence is required before preservation can be claimed. This philosophy creates no Evaluation Platform.

## 4. Harvest is a lifecycle verb

`HARVEST` means preserving sufficiently understood, evidence-backed, valuable capability from a temporary implementation, Agent, project, method, or human-AI collaboration as a reusable organizational asset. **Harvest is a lifecycle verb, not a Platform object.**

This does not create a Harvest Engine, Harvest Service, Harvest Registry, Harvest Manager, Harvest Platform, or Harvest object model. Capability that is not sufficiently proven should not be harvested. A harvested capability may be reused, recomposed, rebound, updated, superseded, replaced, or evaluated again; harvest does not imply permanence.

## 5. Humans and collaboration are capability sources

People, Agents, external tools, projects, workflows, human expertise, and human-AI collaboration can all contribute useful capability. Experience is not automatically organizational capability. A selective, governed lifecycle is:

`REAL WORK → EXPRESSION / OBSERVATION → UNDERSTANDING → EVIDENCE → REPEATED USEFULNESS → EVALUATION → HARVEST`

This is not surveillance, automatic employee extraction, or automatic ownership assignment. Human contribution and organizational preservation require appropriate governance, consent, attribution, and evidence.

## 6. Harness as an evidence-producing aid

A Harness can provide deeper value when it is bounded, inspectable, reproducible where required, and able to produce evidence. That makes a capability easier to evaluate and potentially preserve:

`AI CREATION → GOVERNED PRODUCTION → INSPECTABLE RESULT → EVIDENCE → EVALUATION → POSSIBLE HARVEST`

The Harness remains replaceable and is not privileged. This sequence is an explanatory pattern, not a new Harness contract or mandatory pipeline.

## 7. Real-use evolution

Capability should be considered through the recurring real-use cycle:

`REAL USE → OBSERVE → UNDERSTAND → EVALUATE → EVOLVE → REAL USE AGAIN`

This is a design interpretation, not a mandatory Platform pipeline or object model. Benchmark evidence and real-use evidence can both contribute, subject to the applicable authority and evidence requirements.

## 8. Harvest as metaphor, not ontology

The Catalyst/Harvest metaphor is explicitly **METAPHOR, NOT ONTOLOGY**. It supplies language for selective preservation and evolution. It does not introduce Seed, Crop, Growth, or Harvest managers, objects, layers, or registries.

## Closing principle

Catalyst should make it increasingly possible for valuable capability to be understood, evaluated, preserved, recomposed, and evolved without rebuilding accumulated learning whenever technology changes. This philosophy describes that direction; it does not claim that Catalyst already provides a universal capability-harvest implementation.
