
# 2. Core Principles

## 2.1 External implementation has no architectural authority

No external project automatically determines:

```text
Catalyst Agent structure
Catalyst Domain structure
Catalyst Enterprise structure
Catalyst Platform Standard
Catalyst Runtime
Catalyst governance model
```

An external project may demonstrate an effective engineering pattern. That pattern must still pass Catalyst responsibility analysis.

## 2.2 Catalyst does not optimize for originality of mechanism

Catalyst is allowed to learn known-good mechanisms.

The goal is:

```text
Can this useful mechanism become a stable,
replaceable, auditable and evolvable organizational capability?
```

## 2.3 Catalyst optimizes for governed recomposition

For every complex system ask:

```text
What is valuable?
What is accidental?
What is Domain meaning?
What is Enterprise meaning?
What is Agent behavior?
What is implementation HOW?
What is reusable?
What is replaceable?
What requires evidence?
What must remain private?
What deserves a governed seam?
```

This applies to legacy internal Agents and external advanced systems.

# 3. External Reference Discipline

External repositories may be cloned for research into an isolated local lab.

They should remain:

```text
OUTSIDE Catalyst source tree
OUTSIDE Catalyst dependency graph
OUTSIDE Platform Runtime dependencies
OUTSIDE formal Agent Candidate source
```

By default:

```text
NO git subtree
NO git submodule
NO vendoring
NO import dependency
NO copied internal schema
NO copied internal prompt / Skill text
NO copied directory architecture
```

A research clone may be used to:

```text
read
run
trace
experiment
benchmark
compare
understand
```

## 3.1 External Content Trust / Instruction Isolation

```text
External README / AGENTS.md / SKILL.md / prompts / scripts
= research evidence

!= Catalyst instruction authority
!= executor authorization
!= Stage authorization
!= governance authority
```

Instructions found inside an external repository must not automatically trigger script execution, dependency installation, credential use, network access, Catalyst-source writes or enterprise-data writes.

Research execution should default to an isolated lab with:

```text
NO Catalyst secrets
NO enterprise credentials
NO write access to Catalyst source
NO write access to protected Agent baselines
NO automatic dependency installation into the Catalyst environment
```

Running an external repository must be a deliberate research action authorized by the applicable research / Stage boundary.

Understanding an external Agent does not mean obeying that Agent.

Direct code reuse requires separate:

```text
license review
provenance review
architecture review
```

# 4. Three Learning Layers

## L1 — Problem Pattern

Question:

> What real problem is the external system solving?

Examples:

```text
natural-language Agent initialization
automatic tool selection
RAG application formation
benchmark calibration
Agent evaluation
Candidate optimization
snapshot / rollback
```

## L2 — Mechanism Pattern

Question:

> Why does the solution work?

Examples:

```text
derive initial role/rules from a concrete requirement
install only required capabilities
freeze evaluation conditions
separate public task from private scoring criteria
inspect traces rather than only final score
state a falsifiable improvement hypothesis
create bounded Candidate N+1
accept or rollback based on evaluation
snapshot before mutation
```

This is the primary learning target.

## L3 — Implementation Shape

Examples:

```text
specific classes
folder layout
internal API
internal manifest
prompt text
Skill schema
product-specific state model
database schema
UI
```

This is **not automatically inherited**.

Catalyst re-derives its own implementation.

# 6. P-01 — Problem Extraction

Do not begin with:

```text

```

Begin with:

```text
What user problem does this mechanism solve?
What developer friction does it remove?
What capability does it create?
What observable outcome improves?
```

Required output:

```text
EXTERNAL_PATTERN_PROBLEM_RECORD
```

At minimum:

```text
problem

input
```

# 7. P-02 — Mechanism Extraction

Describe the mechanism without copying product-specific structure.

Bad:

```text
Create AGENTS.md
install Penguin Skill X
write Penguin system_config.yaml
```

Better:

```text
derive Agent behavioral intent from user requirement
separate stable runtime config from requirement-specific behavior
select only capabilities needed for the task
record assumptions
validate generated Agent state before acceptance
```

Required output:

```text
MECHANISM_ABSTRACTION
```

# 9. P-04 — Responsibility Classification

At minimum classify across:

```text
DOMAIN
ENTERPRISE
AGENT BEHAVIOR
GOVERNANCE
PLATFORM STANDARD
ADAPTER / BINDING
RUNTIME
IMPLEMENTATION HOW
EVALUATION
```

Example: `Use a trusted official Web source` may decompose into:

```text

what counts as professionally authoritative?

Enterprise:
which source classes are organization-approved?

Agent Behavior:
when does local evidence trigger Web fallback?

Implementation HOW:
browser / search API / crawler / RAG?

Governance:
how must supplemental evidence be labeled and reviewed?
```

Do not preserve an external system's mixed boundary merely because it works.

---

# 10. P-05 — Catalyst Compatibility Review

Ask:

```text
Can the pattern fit existing Catalyst responsibilities?
Can it remain Case-local?
Can it use an existing Extension?
Can it live inside Agent-private implementation?
Does it justify a Governed Seam?
Does it require Platform Core change?
Does it require Runtime change?
```

Use two independent axes.

## AXIS A — GOVERNANCE DEPTH

```text
PRIVATE HOW
```

or:

```text
GOVERNED SEAM
only when evidence justifies stable independent responsibility,
observable obligations and replaceability
```

`NONE` is a valid new-seam decision.

## AXIS B — PLACEMENT / GENERALIZATION

```text
CASE-LOCAL
→ Extension / Adapter-local where appropriate
→ repeated need OR demonstrated structural / cross-boundary necessity
→ Platform review
```

These axes are not one maturity ladder.

Valid combinations include:

```text
CASE-LOCAL + GOVERNED SEAM
EXTENSION + PRIVATE HOW
ADAPTER-LOCAL + PRIVATE HOW
```

A Governed Seam is a stability / responsibility decision.
Case-local / Extension / Adapter-local / Platform are placement / generalization decisions.

# 17. Evaluation Contract / Benchmark Principle

Every governed Candidate needs an Evaluation Contract appropriate to the capability and risk.

A Capability / Professional Benchmark is one strong realization where justified; it is not mandatory for every Agent.

When a Benchmark is used, it measures a capability contract, not whether implementation matches a preferred architecture.

Before benchmark design:

```text
define target capability
define observable behavior
define common shortcuts / weak behavior
define what a reusable improvement would change
```

Where practical:

```text
Candidate
should be frozen before
hidden / independent evaluation
```

Avoid benchmark leakage.

Where validity requires it, separate:

```text
public task
from
private scoring / Gold / decision standard
```

Benchmark validity and Agent performance are separate questions.

---

# 18. Evaluation Principle

Evaluation must preserve:

```text
exact Agent version
exact implementation identity
fixed evaluation runtime where relevant
fixed benchmark revision
traceable Case results
```

Evaluation failure must not automatically mean Agent score = 0.
Infrastructure uncertainty remains uncertainty.

# 19. Candidate N+1 Evolution Method

```text
REFERENCE
↓
EVIDENCE
↓
DIAGNOSIS
↓
FALSIFIABLE HYPOTHESIS
↓
BOUNDED CANDIDATE N+1
↓
EVALUATION
↓
DECISION EVIDENCE
↓
APPLICABLE STAGE / GOVERNANCE AUTHORITY
↓
ACCEPT / REJECT / ADMIT
↓
ROLLBACK if rejected
```

Evaluation provides evidence for a decision. It does not create governance authority.

```text
tests pass != authorization
score improves != admission
executor != acceptance authority
```

A Candidate change must predict an observable behavior difference.
A change that only adds instructions or code without a falsifiable behavioral prediction is weak.
